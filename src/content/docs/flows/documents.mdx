A family's documents are the evidence behind every number. The flow is built around one
idea: **a machine may read, but only a person may believe.**

## The gate

<div class="defs not-content">
  <div><dt>The real file type</dt><dd>The type is detected from the file's own leading bytes. The label the uploader supplied is only a hint and is never trusted, so a program renamed to look like a statement is rejected.</dd></div>
  <div><dt>Malware scan</dt><dd>A document is quarantined until scanned. An unscanned document cannot be accepted into the pipeline.</dd></div>
  <div><dt>Storage</dt><dd>Stored under a per-client key, encrypted, with a checksum recorded on write and checked again on read. Stored objects are written once and never overwritten.</dd></div>
  <div><dt>Text recognition</dt><dd>Plain documents are read locally. Scanned pages and images go to a recognition provider. If the provider fails, the document fails closed rather than silently skipping the step.</dd></div>
</div>

## The proposal

The assistant reads the text and proposes a document type, and the values it finds, each
with a confidence score. It also flags anything suspicious, such as text that looks like an
attempt to instruct the assistant. Before the assistant sees a document, direct identifiers
are reduced on a best-effort basis. That reduction is a safeguard, not de-identification,
and the product treats every document as fully sensitive regardless.

Proposed values are **observations, not facts**:

<div class="defs not-content">
  <div><dt>Tax return income</dt><dd>An annual figure. Never treated as monthly income without an explicit conversion by a person.</dd></div>
  <div><dt>Pay stub</dt><dd>Covers a stated period that has to be normalised to a month by a person.</dd></div>
  <div><dt>Home value</dt><dd>Not the same as equity. Mortgage balances are debt.</dd></div>
  <div><dt>Trust amounts</dt><dd>Not automatically available assets. Whether and when funds are reachable is a human judgement.</dd></div>
</div>

configuration that turns this off, and the calculation refuses to run on a profile nobody
has verified.

## Reviewing a family's submission

When a family submits, staff open the submission and work through it document by document.

<Shot
  src="/img/shots/submission-review.webp"
  route="/submissions/{id}"
  role="Finance reviewer"
  caption="<b>Reviewing a submission.</b> Each document shows what was detected, the family's own label, the extracted figure and its confidence, with Verify and Reject. The activity panel on the right is the trail the family can also see."
/>

<div class="defs not-content">
  <div><dt>Verify</dt><dd>Confirms the type and the figures. A document must be verified before its figures can inform a calculation.</dd></div>
  <div><dt>Reject</dt><dd>Marks it unusable, with a reason. The counselor can ask the family for a replacement.</dd></div>
  <div><dt>Validate the financials</dt><dd>A person with the financial scope confirms the income, assets and benefit figures as a whole. A counselor can run the conversation but cannot do this step.</dd></div>
  <div><dt>Accept</dt><dd>Blocked while any requested document is missing, unscanned or unreviewed.</dd></div>
</div>

## Promotion

Promotion is one explicit step. It creates the resident record, copies the verified
documents across to their permanent location, and carries the validated financial profile
with it. If the financials were validated they arrive ready to assess. Otherwise a person
still has to confirm them in the workspace. From this moment the family portal has no
further reach into the record.
