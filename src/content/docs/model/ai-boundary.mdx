Language models are probabilistic, non-reproducible and opaque. Those are unacceptable
properties for a **decision** about whether someone can live somewhere, and exactly the
properties that make them useful for **reading and writing**. The product draws one hard
line between the two.

> **Deterministic arithmetic, probabilistic language.**

## Why the boundary is structural

A boundary described in a prompt is a hope. These are mechanisms:

<div class="defs not-content">
  <div><dt>The calculation's input is a strict shape</dt><dd>Any unknown field is rejected, so protected-class attributes such as age, birth date, name, identity number and diagnosis cannot be smuggled into the decision path. Tests assert that they never appear in it.</dd></div>
  <div><dt>Extraction carries a fixed flag</dt><dd>Every extraction result says a human must review it. The value is fixed, not configurable. The calculation additionally refuses to run on a profile no person has verified.</dd></div>
  <div><dt>The summary is downstream and inert</dt><dd>The assistant receives a minimised projection of the result, with no names and no account numbers. Its prose is stored beside the result and never inside it, so it cannot alter a figure.</dd></div>
  <div><dt>Tier and outcome are produced by one place</dt><dd>Only the deterministic calculation computes them. The assistant has no path to set them.</dd></div>
</div>

## Protecting what it reads

<div class="split not-content">
  <div class="panel">
    <h4>Reduction before the model</h4>
    <p>Direct identifiers are reduced on a best-effort basis before a document reaches the model, and text that looks like an attempt to instruct the assistant is flagged. This is a safeguard, not de-identification, and every document is still treated as fully sensitive.</p>
  </div>
  <div class="panel">
    <h4>Grounding</h4>
    <p>What comes back is checked against the figures it was given, so a summary that drifts from the result can be caught.</p>
  </div>
  <div class="panel">
    <h4>Approval before use</h4>
    <p>A live provider is only used after the exact arrangement, including retention and the agreement covering sensitive data, has been approved for the organisation. Until then the product refuses to process documents through one.</p>
  </div>
</div>

## It can run with no model at all

The product ships with a **deterministic stand-in** for the assistant. With it, every screen
works, every flow completes and every test runs without a single external call. Extraction
returns predictable values and summaries are templated from the figures.

That is more than a convenience. It means the correctness of the product never depends on
a model being available, and a model outage degrades a nicety rather than blocking a case.

## When the assistant is wrong

It will sometimes be wrong, and the design assumes so.

<div class="defs not-content">
  <div><dt>A misread figure</dt><dd>It lands in the review queue or on a document screen with a confidence score. A person confirms or corrects it before it can matter.</dd></div>
  <div><dt>A poor summary</dt><dd>It is words beside a result. The figures and the tier are unaffected, and the person reading can see both.</dd></div>
  <div><dt>An attempted manipulation</dt><dd>Text embedded in a document that tries to steer the assistant is flagged, and in any case the assistant has nothing to steer: it cannot change a number or a decision.</dd></div>
</div>
