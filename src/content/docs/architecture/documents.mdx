Documents are the most hostile input the product accepts. They come from people outside the
organisation, they can be crafted, and they contain the most sensitive data it holds. They
are handled accordingly.

## Ingestion

<div class="defs not-content">
  <div><dt>The real type</dt><dd>The file's type is detected from its leading bytes. The label a person supplied, and any extension, are hints only. A document that is not what it claims to be is rejected.</dd></div>
  <div><dt>Malware scanning</dt><dd>A document is held until scanned. An unscanned document cannot be accepted into the pipeline, and a rescan task exists for documents left pending.</dd></div>
  <div><dt>Storage</dt><dd>The object is written under a key that includes the client, with encryption and a recorded checksum. Writes are conditional and immutable: an existing object is never overwritten.</dd></div>
  <div><dt>Size and shape</dt><dd>Uploads are bounded, and content is checked rather than trusted.</dd></div>
</div>

## Text recognition

Plain documents are read locally. Scanned pages and images can go to a recognition
provider. The provider sits behind an interface, so it can be changed without touching the
flow, and a failure of a live provider **fails closed** instead of silently falling back to
guessing. Which formats the configured provider supports is checked up front, so an
unsupported file is refused with a clear message.

## Retrieval

<div class="defs not-content">
  <div><dt>Authorisation by kind</dt><dd>Reading content requires the scope the document's kind needs: financial, medical, or both for an unrecognised one. Both the declared kind and the inferred kind are considered, so relabelling cannot lower the protection.</dd></div>
  <div><dt>Verification on read</dt><dd>The stored checksum is validated when the object is read, so silent corruption or substitution is detected.</dd></div>
  <div><dt>Safe delivery</dt><dd>The file is served with a content disposition that prevents it being interpreted as something executable, and with headers that stop it being cached.</dd></div>
  <div><dt>Every read is audited</dt><dd>With the document and the actor.</dd></div>
</div>

## Promotion

When staff accept a family's submission, its documents move from staging to their
permanent home.

<ol class="steps not-content">
  <li><h4>Copy to deterministic keys</h4><p>Each staged object is copied to a canonical key outside the database transaction, so the transaction stays short.</p></li>
  <li><h4>Re-verify the source</h4><p>The source object's checksum is checked again against what was recorded at upload, so nothing swapped in the meantime is promoted.</p></li>
  <li><h4>Commit the records</h4><p>Only then does the transaction create the resident's document records.</p></li>
</ol>

Only documents a person has verified are promoted, and "nothing is promoted unvalidated" is a
rule of the flow, not a convention.

## Keys that must keep working

Documents and fields use versioned encryption identifiers. When keys are rotated, stored
ciphertext remains readable by the retired key, and a maintenance task re-encrypts stale
rows under the active one. See <a href="/operations/keys/">Keys and rotation</a>.
