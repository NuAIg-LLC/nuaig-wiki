## What each part is responsible for

<div class="defs not-content">
  <div><dt>Staff workspace</dt><dd>The internal application. It is a server-side client: the staff member's credential and session live on the server in an encrypted cookie, and the browser never holds an access token. It composes screens from the records service and enforces nothing of its own.</dd></div>
  <div><dt>Family portal</dt><dd>The external application. It runs as its own database identity that can reach only the staging area, so a bug in it can disclose at worst one family's own staged answers.</dd></div>
  <div><dt>Records service</dt><dd>The one place where every rule is enforced: who the caller is, what they may see, which community they act in, whether a change is current, what a calculation returns, which approvals exist, and what is recorded. It is the only writer of business records.</dd></div>
  <div><dt>Calculation</dt><dd>Two deterministic models, versioned, pure and free of side effects, called by the records service. See <a href="/model/engines/">Two models, one product</a>.</dd></div>
  <div><dt>Analytics service</dt><dd>A stateless, advisory probability service. It has no database credential and keeps nothing. It is handed a household and returns a distribution. See <a href="/model/simulation/">Advanced analysis</a>.</dd></div>
  <div><dt>Delivery worker</dt><dd>Drains the message queue and talks to email and text providers, recording the outcome. It has its own narrow database identity. See <a href="/interfaces/notifications/">Notifications</a>.</dd></div>
  <div><dt>Tool surface</dt><dd>An optional, read-mostly surface for automated clients. See <a href="/interfaces/agents/">Agent and tool access</a>.</dd></div>
</div>

## The stores

<div class="defs not-content">
  <div><dt>Records store</dt><dd>A relational database holding every record. It enforces isolation between clients and communities itself, and several tables accept inserts only. See <a href="/architecture/data-model/">Data model</a>.</dd></div>
  <div><dt>Document store</dt><dd>An object store holding uploaded files under per-client keys, encrypted, written once and checked by checksum on read. Small development fixtures may live in the records store.</dd></div>
  <div><dt>Keys and secrets</dt><dd>Field encryption keys, session keys and signing secrets, held as versioned secrets that can be rotated. See <a href="/operations/keys/">Keys and rotation</a>.</dd></div>
</div>

## The edge, outside the platform

Protection in front of the platform, such as filtering of abusive traffic, network access
control and stripping sensitive data from logs and addresses, is deliberately kept as an
**edge** concern. It sits in front of the platform and does not persist any resident data.
Resident data is processed and stored only on infrastructure covered by the agreements that
must cover it. This split keeps the question "where does regulated data live" short and
checkable.

## Three database identities

The platform's runtime components never share a database identity. Each gets only what its
job needs.

| Identity | Used by | Can reach |
| --- | --- | --- |
| Application | The records service | Business records, within client and community isolation |
| Portal | The family portal | The staging area only. No resident record and no audit trail |
| Notification worker | The delivery worker | The message queue, delivery events and suppression records |

A fourth identity, the owner, runs migrations and nothing else. It is never used while the
platform is serving requests. See <a href="/architecture/isolation/">Isolation and tenancy</a>.

## How a request flows

<ol class="steps not-content">
  <li><h4>A client calls the interface</h4><p>With a credential, the community in use, and for changes an idempotency key and revision.</p></li>
  <li><h4>The caller is identified and authority is loaded</h4><p>Person, organisation, role and memberships, from the store, every time.</p></li>
  <li><h4>A transaction opens inside the right isolation context</h4><p>The organisation, and for resident work the community, are set for that transaction only.</p></li>
  <li><h4>The scope check runs</h4><p>The caller must hold the needed permission.</p></li>
  <li><h4>The work is done</h4><p>Records are read or written, calculations run, and any message is queued.</p></li>
  <li><h4>The response is masked and audited</h4><p>Withheld fields are removed, and the access is appended to the ledger in the same transaction.</p></li>
</ol>
